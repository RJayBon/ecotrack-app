## How this scan was done

No Dart/Flutter SDK is installable in this environment (`storage.googleapis.com` is
blocked, so neither the Dart SDK archive nor the Flutter toolchain can be fetched).
`flutter analyze` / `flutter test` therefore could **not** be executed. Instead:

1. **Real syntax validation** — compiled the `tree-sitter-dart` grammar from source
   (gcc) and parsed all 37 Dart files: **0 syntax errors, 0 missing nodes**.
2. **Semantic cross-referencing** (custom scripts) — every import resolved; every
   `DatabaseHelper` method called from the UI/test layer checked against its
   declarations (**0 unknown methods**); every `insert`/`update` map key and every
   raw-SQL identifier checked against the parsed `CREATE TABLE` schema
   (**0 unknown tables or columns**); all 20 seeded icon keys resolve in `icon_map`.
3. **Async/lifecycle analysis** — brace-matched scan of every `async` body for
   `setState`/`context`/`Navigator` use across an unguarded `await`; controller,
   `TabController` and `Timer` create-vs-dispose matching (**no leaks**).
4. **Numeric WCAG verification** — every contrast ratio claimed in `theme.dart`
   recomputed from the hex values, plus every foreground/background pair actually
   used in the widgets (alpha-composited over the real backdrop).
5. **Claim audit** — the 25 "found clean" assertions in `DEEP_SCAN_REPORT.md`
   §15/§16.7 re-tested against the current tree.

Findings are ordered by impact. Nothing already listed as fixed in
`DEEP_SCAN_REPORT.md` is repeated unless the fix did not actually land.

## A. Blockers — the repo cannot be built or run as documented

### A1. All platform folders are missing
`android/`, `ios/`, `web/`, `windows/`, `linux/`, `macos/` do not exist, and there
is no `.metadata`. `README.md` says to run:

```
flutter pub get
flutter run
```

`flutter run` fails immediately — there is no target platform to build for. The
contributor has to know to run `flutter create --platforms=android,ios,web,windows,linux,macos .`
first, which is documented nowhere (see A6).

Knock-on: `pubspec.yaml:64-66` sets `flutter_launcher_icons: android: true, ios: true`,
so `dart run flutter_launcher_icons` has no `android/`/`ios/` resource trees to write into.

### A2. No `.gitignore` — and the report says one was added
`DEEP_SCAN_REPORT.md:698` states "**`.gitignore` added.** … `.dart_tool/`, `build/`,
`.flutter-plugins*`, IDE folders, coverage output and the local `*.db` scratch files
would all be staged". `git ls-files` returns 44 files and no `.gitignore` exists on
disk. The fix was never committed. The very next `git add .` in a working checkout
commits the build tree.

### A3. Web is a supported platform but cannot be set up
`lib/db/database_factory_web.dart:5-11` and `lib/main.dart:52-53` instruct the user to
run `dart run sqflite_common_ffi_web:setup`, which writes `web/sqlite3.wasm` and
`web/sqflite_sw.js`. There is no `web/` directory, and A1 means nothing creates one.

## B. High — runtime defects

### B1. `login_screen.dart` — a DB error during login bricks the login screen
**File:** `lib/screens/login_screen.dart:38-95` (`_login()`)

There is no `try`/`catch`. If `authenticate()` throws — database not openable, missing
`libsqlite3` on Linux, absent web wasm assets, a failed migration, a corrupt file — the
exception escapes as an unhandled async error and:

- `_loading` stays `true` forever → `onPressed: _loading ? null : _login` (line 183)
  keeps the Log In button **permanently disabled with a spinner**;
- `_error` stays `null` → **no message is shown**, so the screen looks like it is
  still thinking;
- the user's only escape is killing the process.

This is the app's front door, and it is the one screen that cannot be navigated away from.
The identical hazard was fixed in `admin_setup_screen.dart:57-68` (the "DEFECT FIX"
comment describes exactly this symptom) — the fix never reached `login_screen.dart`.

### B3. `setState()` after an `await` with no `mounted` guard → framework error
`analysis_options.yaml:15` raises `use_build_context_synchronously` to **error**, but
that lint only covers `BuildContext`, not `setState`. These two slip through the
analyzer and throw `setState() called after dispose()` at runtime:

**1. `lib/screens/admin/admin_tenant_form_screen.dart:67`**
```dart
final exists = await DatabaseHelper.instance.usernameExists(_usernameCtrl.text.trim());
if (exists) {
  setState(() => _saving = false);        // ← line 67: NO mounted check
  if (mounted) showErrorSnack(context, 'Username already taken.');   // ← line 68: guarded
```
The next line *is* guarded, so the hazard was understood but the guard was applied to
the wrong statement — and the file's own comment at line 79 says "Every setState /
context use needs a mounted check".
**Trigger:** Add Tenant → duplicate username → tap Create → press Back while the query
is in flight.

**2. `lib/screens/tenant/tenant_rewards_screen.dart:84`**
```dart

if (!confirmed) return;
setState(() => _busyRewardId = reward.id);               // ← line 84: NO mounted check
```
**Trigger:** tap Redeem, then leave the Rewards tab (bottom-nav switch re-parents the
`IndexedStack`) or back out before confirming.

### B5. Tenant deactivation is only enforced at login — not while a session is live
`lib/screens/login_screen.dart:84-90` correctly refuses to sign in an `inactive` tenant,
and `lib/screens/admin/admin_tenant_detail_screen.dart:71-73` tells the admin the tenant
"will no longer be able to log in until reactivated".

But neither `DatabaseHelper.completeActivity` (`lib/db/database_helper.dart:990`) nor
`DatabaseHelper.redeemReward` (`:1094`) reads `tenants.status`. Nothing re-validates the
session either. So a tenant who is **already signed in** when an admin deactivates them
keeps earning and spending Eco Points indefinitely — the deactivation has no effect until
they happen to log out. `redeemReward` re-reads the *reward* row inside its transaction
(`:1103`) but not the tenant's status (`:1101` reads only `total_points`).

## D. Accessibility — measured, not eyeballed

`theme.dart:5-8` asserts "Every value below was checked against the WCAG 2.1 contrast
minimums" and `DEEP_SCAN_REPORT.md:519` (item 8) records "Every text pairing meets AA."
Recomputing every pair actually used by the widgets:

### D1. `common_widgets.dart:368` — the "Active" status pill fails AA by 0.01
`StatusBadge` paints `AppColors.primary` text on a **10 %** primary tint over white =
**4.49:1**. AA needs 4.5 for 12 px text. `EcoPill` in the same file (line 117) was
deliberately moved from a 12 % to an **8 %** tint for exactly this reason — its doc
comment at line 105 says 8 % yields "primary 4.63:1 … instead of landing just short
at 4.36:1" — but `StatusBadge` was left at 10 %. **Fix:** use `alpha: 0.08` here too (4.63:1).

### D2. `tenant_home_tab.dart:105-111` — the unread badge fails AA badly
9 px white text on `Colors.redAccent` (`#FF1744`) = **3.85:1** (needs 4.5). This is also
the only place a raw, un-vetted Material colour is used as a text pair; the palette's own
`AppColors.danger` gives white-on-it **5.62:1** and is used for exactly this role elsewhere.

### D3. `admin_activities_screen.dart:120` and `admin_rewards_screen.dart:119` — archived rows fail AA
Both wrap the entire card content in `Opacity(opacity: 0.65)`. Composited over white that
drops:
- body text (`textMuted`) → effective `#97A198` = **2.67:1** (needs 4.5)
- the "+N pts" pill → effective `#77AA7A` = **2.69:1** (needs 4.5)
- title (`textDark`) → `#6B756C` = 4.79:1 (still passes)

The archive feature was added after the theme's WCAG pass and silently defeated it for
every archived item. **Fix:** dim only the avatar/icon, or switch archived text to a
token that still clears AA at 0.65.

### D4. `tenant_rewards_screen.dart:202-205` — disabled Redeem button = 3.49:1
`Colors.grey.shade600` on `Colors.grey.shade300` at 11.5 px. Formally exempt (WCAG 1.4.3
excludes inactive controls), but this label is the *only* thing distinguishing "you can't
afford this" ("Locked") from "Out of stock", and it is close to illegible. Also two more
raw Material colours outside the vetted palette.
